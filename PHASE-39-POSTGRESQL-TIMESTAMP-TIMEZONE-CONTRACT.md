# Phase 39 — PostgreSQL timestamp and timezone contract

**Status:** Static contract audit and regression tests only.  
**Base:** Phase 38 poll-integrity branch.  
**Safety:** No PostgreSQL connection, SQL execution, data conversion, Supabase change, Render change, merge, or deployment.

## Findings from the current application

1. SQLite-generated `CURRENT_TIMESTAMP` values are UTC timestamps represented as text without an offset. The Moments table also uses SQLite `datetime('now', '+24 hours')`, which is UTC-based.
2. Group invitation expiry values are generated by JavaScript `Date.prototype.toISOString()`, so they include an explicit UTC `Z` suffix.
3. Group event creation rejects timestamps without an explicit `Z` or numeric offset, parses the supplied instant, and stores `toISOString()`. Event start times therefore represent unambiguous instants, not local wall-clock values.
4. The reminder worker compares event instants to `new Date().toISOString()`. Its SQLite `julianday()` query must be rewritten using PostgreSQL timestamp comparisons; the reminder claiming operation must remain atomic and deduplicated.
5. The current SQLite API exposes a mixture of timestamp strings: SQLite `CURRENT_TIMESTAMP` values and ISO strings created by JavaScript. The PostgreSQL API must deliberately normalize timestamp serialization rather than relying on driver defaults.

## Required PostgreSQL policy

- Store instants in `TIMESTAMPTZ`; do not use `TIMESTAMP WITHOUT TIME ZONE` for these event/creation/expiry/receipt fields.
- Treat legacy SQLite values generated by `CURRENT_TIMESTAMP` or `datetime('now', ...)` as UTC. During migration, explicitly interpret naive legacy timestamp text as UTC (for example, attach `+00:00` before casting); never let the migration session timezone decide.
- Preserve ISO strings that already include `Z` or an explicit numeric offset as the same instant.
- Continue requiring an explicit offset on newly submitted event start times. Do not reinterpret a naive date-time as Ethiopia time.
- Use UTC instants for storage and server-side scheduling. Ethiopia's `Africa/Addis_Ababa` timezone (UTC+03:00) is a display/input presentation choice only; if a future UI accepts local wall-clock input, it must explicitly attach that IANA timezone before converting to an instant.
- Return API timestamps in a consistent ISO-8601 UTC form (for example, `2026-11-10T18:30:00.000Z`) after PostgreSQL integration, and add API contract tests before switching clients.
- Use PostgreSQL `CURRENT_TIMESTAMP` / `now()` and direct `TIMESTAMPTZ` comparisons for expiry and reminder windows. Do not carry over SQLite `datetime()` or `julianday()` expressions.
- Keep timestamp conversion separate from BIGINT ID conversion; IDs must remain strings where node-postgres returns BIGINT strings.

## Timestamp columns covered by the draft schema

`created_at`, `updated_at`, `joined_at`, `delivered_at`, `read_at`, `edited_at`, `deleted_at`, `pinned_at`, `expires_at`, `revoked_at`, `hidden_at`, `reviewed_at`, `closed_at`, `starts_at`, and `cancelled_at`.

All timestamp column declarations in the PostgreSQL draft must remain `TIMESTAMPTZ`.

## Remaining gates before a real migration

- Build a one-time data conversion that explicitly handles both legacy UTC-naive SQLite strings and offset-bearing ISO strings, with invalid-value reporting and a dry-run mode.
- Test round-trip conversion at UTC boundaries, Ethiopian UTC+03:00 display, daylight/timezone offsets, expiry boundaries, and reminder windows.
- Rewrite the reminder worker to asynchronous PostgreSQL queries and a transaction/unique-key claim that prevents duplicate notifications across multiple worker instances.
- Convert every remaining route and Socket.IO database operation; the current application is still synchronous SQLite.
- Verify PostgreSQL serialization and behavior against a disposable test database before any live data migration.
- Take and verify independent backups before migrating any existing test-user data.

**Conclusion:** Timestamp semantics are sufficiently established for a documented migration policy: legacy SQLite-generated naive timestamps are UTC, while event/invitation timestamps already carry explicit UTC offsets. This phase does not make the application public-ready and does not authorize running the DDL.
