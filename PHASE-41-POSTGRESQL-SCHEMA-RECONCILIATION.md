# Phase 41 — SQLite to PostgreSQL schema reconciliation

Status: static source review and automated contract checks only. No database was connected to or changed.

## Scope and method

Compared the application schema assembled by `src/db.js` (including its conditional `ALTER TABLE` additions and later table declarations) with `migrations/postgres/001_initial_schema.sql`. This is a source-level reconciliation, not a live schema inspection. The SQLite file is an evolving bootstrap/migration script; the PostgreSQL file is a fresh-schema draft.

The review covers the 29 application tables, key columns, primary keys, foreign keys, checks, defaults, indexes, timestamp semantics, and legacy initialization behavior.

## Confirmed mappings and intentional hardening

- SQLite integer auto-increment IDs map to PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Preserve IDs during import and explicitly synchronize identity sequences after loading.
- SQLite timestamp text columns map to `TIMESTAMPTZ`, consistent with Phase 39. Legacy SQLite timestamp strings without an offset must be interpreted as UTC; offset-bearing timestamps represent their actual instants. API timestamps should remain ISO-8601 UTC.
- SQLite integer boolean-like fields `notifications.is_read`, `groups.approval_required`, `group_polls.multiple_choice`, and `group_messages.is_announcement` map to `SMALLINT` with 0/1 checks where the source schema has checks. Do not silently convert API values or change existing semantics.
- SQLite `length(...)` constraints are represented using PostgreSQL `char_length(...)` checks.
- Case-insensitive username uniqueness is represented by a unique index on `LOWER(username)`, replacing SQLite `COLLATE NOCASE UNIQUE`. Confirm the application's exact username normalization and accepted Unicode behavior before cutover; SQLite NOCASE and PostgreSQL LOWER are not guaranteed to be identical for every Unicode character.
- The PostgreSQL poll-vote constraint is intentionally stronger than the legacy SQLite definition: the composite foreign key `(poll_id, option_id)` ensures that a vote cannot pair one poll with an option belonging to another poll. Phase 38 adds the supporting unique key on `group_poll_options(poll_id,id)`. Preserve this protection.
- The PostgreSQL Moments expiry default uses `CURRENT_TIMESTAMP + INTERVAL '24 hours'`, corresponding to the SQLite UTC-based 24-hour expiry rule.
- The group-message receipt, message reply, group-message reply, pinned-message, announcement, and other later-added fields are included in the PostgreSQL schema even though SQLite introduces several of them through conditional `ALTER TABLE` statements.

## Migration-sensitive behavior not represented by DDL alone

1. **Legacy schema evolution:** `src/db.js` conditionally adds profile, message, group-message, and group columns. A data migration must inspect the actual source database and export every present column; do not assume every deployed SQLite file has identical age or history.
2. **Historical group receipts:** when `group_message_receipts` did not exist, SQLite bootstrap backfilled receipt rows for eligible historical group messages and members. The migration must first inspect whether the source table exists and preserve its rows. If absent, decide explicitly whether to reproduce the historical backfill; do not run it unconditionally or duplicate rows.
3. **Identity sequences:** after preserving numeric IDs, set each PostgreSQL identity sequence to a value above the maximum imported ID before allowing new inserts.
4. **Username normalization:** compare existing usernames for case-fold collisions under PostgreSQL's chosen uniqueness rule before loading. Report collisions for manual resolution; never silently rename accounts.
5. **Foreign-key validation:** validate orphan counts and all foreign-key relationships before and after import. PostgreSQL's poll composite foreign key may reject legacy cross-poll votes; report these rows for review rather than dropping or rewriting them silently.
6. **SQLite-specific behavior:** source code still uses synchronous better-sqlite3 calls, SQLite placeholders, SQLite date functions, and SQLite transactions. Schema parity does not make application code PostgreSQL-compatible. The route, Socket.IO, and reminder-worker conversion sequence from Phases 33E/40 remains mandatory.

## Review findings / blockers before any live migration

- This is not a proof of equivalence for every deployed SQLite database. A real source-database schema snapshot and row-level preflight are still required, with sensitive values kept out of logs and pull requests.
- Unicode username equivalence needs a product decision and collision report.
- The stricter poll-vote relationship needs a preflight query and explicit remediation for any invalid legacy rows.
- Historical group-receipt behavior needs a source-table-existence check and an idempotent migration decision.
- Identity sequence synchronization must be included in the import procedure.
- Index and query-plan tuning should be validated against representative data after conversion.
- The SQLite runtime remains active; do not set `DATABASE_URL`, execute this DDL on Supabase, or change Render configuration as part of this phase.
